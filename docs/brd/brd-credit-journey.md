## 1. Контекст и бизнес-цель

**Проблема.** В текущем процессе проверка БКИ и предложение страхования разрознены или выполняются поздно → растут Time-to-Decision / Time-to-Cash, падает конверсия и take-rate страховки при риске ухудшения качества решения.

**Цель.** Сократить время от заявки до решения/выдачи и встроить БКИ + оффер страхования в единый цифровой journey без роста просрочки сверх согласованного порога.

**Тип инициативы.** Интеграционный / внедрение нового процесса. Горизонт: 8–12 недель, 2 релиза (MVP → Phase 2).

## 2. Scope

### 2.1. In scope — MVP (Release 1)

- Цифровая заявка на займ (веб/API-канал)
- Обязательные согласия: ПДн + запрос в БКИ (гейт до вызова БКИ)
- Интеграция с одним БКИ: запрос → ответ → интерпретация для решения
- Решение: `approve` / `decline` / `manual_review`
- Оффер займа после approve
- Оффер страхования на шаге выдачи (**opt-in**: отказ от полиса не блокирует выдачу)
- Выдача (зачисление) при accept оффера займа
- Базовый мониторинг SLA и статусов интеграций
- UAT и чек-листы качества по ключевым сценариям

### 2.2. Phase 2 (не в MVP)

- Расширенные правила скоринга / ручной разбор
- A/B офферов страхования
- Повторные запросы / кэш политики БКИ
- Расширенная отчётность для риска и продукта
- Продвинутые компенсирующие сценарии частичных сбоев

### 2.3. Out of scope

- Собственная ML-модель скоринга «с нуля»
- Мобильное приложение с нуля
- Полноценный коллекшен / реструктуризация
- Замена АБС целиком
- Мульти-БКИ

Change control: любое расширение scope — через Продуктовый отдел (A) и PM/BA (R); см. [RACI](../stakeholders-raci.md).

## 4. AS-IS → TO-BE (summary)

Детали: [AS-IS](../processes/as-is-loan-process.md), [TO-BE](../processes/to-be-loan-journey.md).

| Было (AS-IS) | Станет (TO-BE MVP) |
|--------------|-------------------|
| БКИ поздно / вручную | БКИ на критическом пути до решения |
| Согласия неполные | Гейт согласий до БКИ |
| Страховка вне выдачи | Opt-in оффер на шаге выдачи |
| Сбой БКИ → зависание или небезопасный обход | Ретраи → manual review |
| Причины отказа размыты | Справочник кодов |

Целевой поток: анкета → согласия → АБС → БКИ → решение → оффер займа → оффер страховки → выдача → мониторинг.

## 6. Бизнес-требования (MVP)

ID формата `BR-xx`. Приоритет: Must / Should.

### 6.1. Заявка и согласия

| ID | Требование | Приоритет | A |
|----|------------|-----------|---|
| BR-01 | Клиент создаёт заявку на займ в цифровом канале (веб/API) | Must | Продуктовый отдел |
| BR-02 | До вызова БКИ система требует явные согласия на обработку ПДн и на запрос в БКИ | Must | Комплаенс |
| BR-03 | Без действующих согласий заявка не переходит к запросу БКИ | Must | Комплаенс |
| BR-04 | Тексты согласий и отказных сообщений утверждает Комплаенс; в канале отображается утверждённая версия | Must | Комплаенс |
| BR-05 | Неполный набор обязательных полей → дозапрос клиенту; БКИ не вызывается | Must | Продуктовый отдел / IT |

### 6.2. Решение по займу

| ID | Требование | Приоритет | A |
|----|------------|-----------|---|
| BR-10 | После успешного ответа БКИ применяется набор правил Отдела кредитных рисков | Must | Отдел кредитных рисков |
| BR-11 | Возможные исходы авто-решения: `approve`, `decline`, `manual_review` | Must | Отдел кредитных рисков |
| BR-12 | При `decline` клиенту показывается отказ; фиксируется `reason_code` из справочника | Must | Отдел кредитных рисков |
| BR-13 | При `manual_review` заявка попадает в очередь Операционного отдела; approve без актуального ответа БКИ или без явного решения оператора запрещён | Must | Отдел кредитных рисков |
| BR-14 | Оператор в manual review выносит `approve` или `decline` по регламенту; действие аудируется (кто/когда/код) | Must | Операционный отдел |
| BR-15 | Критерии попадания в manual review (помимо таймаута БКИ) | Must | Отдел кредитных рисков — список `[TBD]` |
| BR-16 | Целевой % manual review от потока | Should | `[TBD]` — согласовать с рисками |

### 6.3. Оффер займа и выдача

| ID | Требование | Приоритет | A |
|----|------------|-----------|---|
| BR-20 | При `approve` клиенту показывается оффер займа (сумма, срок, ключевые условия) | Must | Продуктовый отдел |
| BR-21 | Клиент может принять или отклонить оффер займа | Must | Продуктовый отдел |
| BR-22 | При отклонении оффера займа journey завершается; оффер страховки не показывается | Must | Продуктовый отдел |
| BR-23 | При принятии оффера займа инициируется шаг страхования, затем выдача | Must | Продуктовый отдел |
| BR-24 | Успешная выдача фиксирует статусы в АБС; Time-to-Cash считается до подтверждённого зачисления | Must | IT / Продуктовый отдел |

### 6.4. Страхование (opt-in)

| ID | Требование | Приоритет | A |
|----|------------|-----------|---|
| BR-30 | На шаге выдачи (после accept займа) клиенту показывается оффер страхования | Must | Продуктовый отдел |
| BR-31 | Отказ от полиса **не** блокирует выдачу займа | Must | Продуктовый отдел |
| BR-32 | Принятие полиса фиксирует статус оформления у партнёра и в АБС (минимальный набор полей — `[TBD]`) | Must | Продуктовый отдел / IT |
| BR-33 | UX-копирайт и юридические формулировки оффера | Must | Комплаенс + Продукт — тексты `[TBD]` |
| BR-34 | Если страховой API недоступен: сообщение о недоступности, выдача займа без оффера, инцидент в мониторинге | Must | IT / Продуктовый отдел |

## 8. Неуспешные сценарии и fallback

| Сценарий | Поведение MVP | Требование |
|----------|---------------|------------|
| Нет согласий | Стоп до БКИ | BR-02, BR-03 |
| Incomplete поля | Дозапрос; БКИ не вызывать | BR-05 |
| Таймаут/ошибка БКИ после ретраев | → `manual_review` | BR-13; §9 |
| Auto `decline` | Отказ + `reason_code` | BR-12 |
| Reject оффера займа | Конец; без страховки | BR-22 |
| Decline страховки | Выдача без полиса | BR-31 |
| Сбой страхового API | Выдача без оффера + инцидент | BR-34 |
| Сбой зачисления | Статус ошибки выдачи; клиенту понятный статус; ретраи/операционный разбор — политика `[TBD]` | Should → уточнить в Phase 2 / следующей версии BRD |

UAT минимум: approve+страховка; approve без страховки; decline; timeout БКИ → MR; сбой страхового API; reject оффера займа.

## 12. DoR / DoD

### Definition of Ready (требование / story)

- Есть ID, формулировка, приоритет, Accountable-отдел
- Понятен сценарий (happy / alt) и связь с BR-xx

- Приёмка (Given/When/Then или чек-лист) набросана
- Открытые `[TBD]`, блокирующие разработку, эскалированы

### Definition of Done (для поставки по требованию)

- Реализовано согласно BR / story
- Покрыто тестами по согласованному тест-плану QA
- Логи/метрики из §11 пишутся, если требование затрагивает интеграцию
- UAT-сценарий пройден или явно отложен с апрувом Продукта
- Документация/статус в Jira обновлены
